** Digging DNS
*** Hosts file
- simple txt file used to map hostnames to IP addr
- provides manual mehtod of Domain Name Resolution which bypasses DNS.
- =hosts= -> direct local overrides translation of domain names to IP addrs.
- useful for devm troubleshooting, blocking websites.

- Win -> ~C:\Windows\System32\drivers\etc\hosts~

*** Zones
- distinct part of domain namespace.
- virtual container for set of domain names.
- domain & all subdomains belong to same DNS Zone

*** DIG
- =domain information groper=
- =@= -> specifies specific name server to query
- =+trace= -> shows full path of DNS Resolution
- =-x <ip>= -> reverse lookup on IP to find associated hostname
- =+short domain.com= -> short concise answer
- =+noall +answer= -> only answer section of query output
- =ANY= -> all avl DNS records for domain. (many DNS servers ignore =ANY= queries to reduce load and prevent abuse)

;; MSG SIZE  rcvd: 54
#+end_src

1. Header 
   * ~;; ->>HEADER<<- opcode: QUERY, status: NOERROR, id: 16449~
     - indicates type of query(=QUERY=), successful status (=NOERROR=), unique id (=16449=)
   * ~;; flags: qr rd ad; QUERY: 1, ANSWER: 1, AUTHORITY: 0, ADDITIONAL: 0~
     - desc flags in DNS header
     - =qr= -> query response flag (indicates this is response)
     - =rd= -> recursion desired flag (recursion was requested)
     - =ad= -> authentic data flag (resolver considers data authentic)
     - remaining numbers indicate number of entries in each section of DNS response
   * ~;; WARNING: recursion requested but not available~
     - server doesn't support recursion
       
2. Question Section
   * ~;google.com. IN A~
     - ques: what is IPv4 addr (=A=)

3. Answer Section
   * ~google.com.             0       IN      A       142.251.47.142~
     - answer to query.
     - '=0=' -> =TTL= (How long result can be cached before being refreshed)

4. Footer
   * ~;; Query time: 0 msec~
     - time taken for query to be processed & response to be rcvd
   * ~;; SERVER: 172.23.176.1#53(172.23.176.1) (UDP)~
     - IDs DNS server which provided answer & protocol used (UDP)
   * ~;; WHEN: Thu Jun 13 10:45:58 SAST 2024~
     - Timestamp of when query was made
   * ~;; MSG SIZE  rcvd: 54~
     - size of DNS msg rcvd (54B)

5. Opt (*Pseudosection*)
   * extension mechanisms (EDNS) -> allows for larger msg sizes, DNSSEC support

** Subdomains
- extensions of main domain, created to organise & separate different section sor functionalitiesof website

*** Importance
**** Development & Staging Environment
- used by companies to test new features/updates before deploying them to main site
- relaxed security measures -> contain vulns/expose sens info
**** Hidden Login Portals
- subdomains might host admin panels || other login pages not meant to be publicly accessible.
**** Legacy application
- Older & forgotten apps might reside on subdomains -> outdated software w known vulns
**** sensitive info
- subdomains can inadvertently expose confidential docs, internal data, config files

*** Subdomain Enumeration
- from DNS perspective, subdomains repr by =A= or =AAAA= records -> map subdomain name to corresponding IP addr
- =CNAME= records might be used to create aliases for subdomains -> pointing them to other domains/subdomains

***** Active Subdomain Enum
directly interacting w target domain's DNS to uncover subdomains.
1. [[file:20260516161056-footprinting.org::*DIG - AXFR Zone Transfer][DNS Zone Transfer]]
2. [[*Subdomain Brute-force enum][Subdomain Brute-Force Enum]] -> testing list of potential subdomains against target
   - =dnsenum=, =ffuf=, =gobuster=

***** Passive Subdomain Enum
1. =Certificate Transparency Logs=
   - public repos of SSL/TLS certs
   - certs can include list of associated subdomains in *Subject Alternative Name* (SAN) field
2. =search engines=
   - use search operators (=site:=)

**** Subdomain Brute-Force Enum
- leverages pre-defined lists of potential subdomain names.

- Breakdown:
  1) *Wordlist Selection*: selecting wordlist containing potential subdomain names:
     - =General Purpose=: contain broad range of common subdomain names
       # useful when we dont know target's naming convention

     - =Targeted=: focus on specific industries, tech, naming patterns relevant to target.
       # more efficient -> reduce chances of false positives

     - =Custom=: create own wordlist based on specific keywords, patterns intel from other sources.

  2) *Iteration & Querying*: script/tool iterates through wordlist, appending each word/phrase to main domain.

  3) *DNS Lookup*: DNS query performed for each potential subdomain to check if it resolves to an IP. 
     # typically done using A || AAAA

  4) *Filtering & Validation*

** TODO Virtual Hosts
- once DNS directs traffic to correct server, web server config becomes crucial in determining how incoming reqs are handled.
- Web servers are designed to host multiple websites/application on single servers
- achieved through *vhosting*

*** Diff b/w VHost & Subdomains

|----------------------------------------------+---------------------------------------------|
| Subdomain                                    | VHOSTS                                      |
|                                              |                                             |
|----------------------------------------------+---------------------------------------------|
| extension of main domain name                | config w/in webserver which allow multiple  |
|                                              | websites/apps on same shared IP4            |
|                                              |                                             |
| have their own DNS records pointing to       | can be associated with TLDs or subdomains   |
| either same IP as main domain or different   |                                             |
|                                              |                                             |
| used to organise diff sects/servs of website | each VHost can have separate config.        |
|                                              | gives precise control over how reqs handled |
|                                              |                                             |
|----------------------------------------------+---------------------------------------------|

*** Working of VHosts
- ability of web servs to distinguish b/w multiple websites/apps sharing same IP.
- leverages =HTTP Host= header -> included in every =HTTP= request sent by browser.
- if vhost doesn't have dns record, can still access by modifying hosts file

**** VHOST fuzzing
- tehcnique to discover public & non-public =subdomains= and =VHosts= by testing various hostnames against known IP addr.
  
*** Server VHOST Lookup
1. *Browser Requests Website*: initiates HTTP request to webserver associated w domain IP
2. *Host Header Reveals Domain*: browser includes domain name in req's =host= header. Acts as label to inform webserver which website is being requested.
3. *Web Server Determines VHOST*: server rcvs req, examines =host= header, constults VHOST config to find matching entry for domain name
4. *Serving Right Content*: webserver retrieves corresponding files & resources associated w website from document root & sends back to browser as HTTP response
# host header -> switch, enables webserver to dynamically determine which website to serve based on domain name requested by browser

*** Types off VHosting
1. *Name Based*
   - relies solely on =HTTP Host header= to distinguish b/w websites.
   - most common & flexible method.
   - doesn't require multiple IPs
   - cost-effective, easy to setup, supports most modern webservers
   - requires webserver to support name-based vhosting, can have limitations w vertain protocols (SSL/TLS)
2. *IP Based*
   - assigns unique IP addr to each website hosted on server
   - server determines which website to serve based on IP addr to which request was sent
3. *Port Based*
   - diff websites w diff ports on same IP.

** Certificate Transparency Logs
=digital certificate=: file which verifies website's ID & allows for secure & encrypted comms

- =Certificate Transparency= (=CT=) Logs:
  - append only ledgers -> record issuance of SSL/TLS certs.
  - *Global registry of certs*

- whenever a certificate authority issues new cert, it must submit it to multiple CT logs.

- Independent orgs maintain & open for anyone to inspect.

*** Purpose
- *Early detection of Rogue Certs*
- *Accountability for Certificate Aauthorities*
- *Strengthening Web PKI (=Public Key Infra=)*
  
*** How CT Logs Work
1. *Cert Issuance*
   - Website owner req =SSL/TLS= cert from CA
   - CA performs due dilligence to verify owner's ID & domain ownership.
   - after verification, CA issues =pre-certificate=
2. *Log Submission*
   - CA submits =pre-certificate= to multiple CT logs.
   - each log operated by diff org.
   - logs -> append only
3. *Signed Cert Timestamp (SCT)*
   - after recieving =pre-certificate= to multiple CT logs, each CT log generates =Signed Certificate Timestamp=.
   - =SCT= -> cryptographic proof that the cert was submitted to log at specific time.
   - =SCT= included in final certicate issued to website owner.
4. *Browser Verification*
   - user's browser checks cert's =SCT= on connecting to website
   - =SCTs= verified against public CT logs to confirm the cert was issued & logged correctly
   - if =SCT= valid, browser est. secure connection. else -> warning display
5. *Monitoring & Auditing*
   - CT logs continously monitored by various entities:
     - security researchers, website owners, browser vendors.
   - look for anomalies, sus certs

*** Merkle Tree Structure
- ensure CT logs' integrity & tamper-proof nature.
- each leaf node represents cert
- each non-leaf node represents hash of child nodes.
- merkle root = single hash representing entire log.

*** CT Logs & Web Recon
- provide definitive record of certs issued for domain & subdomains
- unveil subdomains associated w old/expired certs -> may host outdated s/w || configs -> potentially vuln to exploitation
